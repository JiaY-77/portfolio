## 记忆是最私人的数据

一个人的记忆里有什么？工作习惯、判断偏好、踩过的坑、对某件事的真实看法、答应过谁什么、哪套方案被否了为什么。

这不是「用户行为数据」，这是**一个人的工作方式本身**。

而主流方案把它放在云上、放在别人的数据库里、用别人定义的格式。我用了一段时间，越想越不对劲。

## 三个具体的风险，不是洁癖

**一、换模型即失忆。**

各家把记忆和应用绑死：记忆存在你的产品里，格式私有，没有导出，或者导出成一堆读不懂的 JSON 嵌套。

这意味着：我用了半年攒下的上下文，在我换一个助手的时候，等于零。我不接受这个——我积累的经验不该被某个产品的存亡绑架。

**二、停服即清零。**

这不是假设。我上一家公司做产品线，公司资金链断了，团队解散，产品下线。用户的数据去哪了？当时的答案是「打包给客户」——但那是因为我们做的是企业服务，有合同约束。

个人工具没有这层保护。一个免费产品的记忆库，说关就关。

**三、记忆里有不该出门的东西。**

我的记忆里有公司项目的表结构、内部流程、还有我对某些事的判断。这些放进任何第三方云，我都得多想两秒。

## 所以我的选择

三条原则：

1. **数据在我自己的机器上**，单文件、可备份、可拷走。用嵌入式数据库而不是远端服务，就是为了让它「拷一个文件就能走」。
2. **格式开放，且能搬迁**。事实是纯文本 + 标准结构；另外做了「记忆包」——一种自包含的 JSON，可以导出、可以在另一台机器上先只读解开看看（校验格式、扫描敏感信息、给人读摘要），再挑着入籍。**默认动作是读，写入必须由人挑选。**
3. **接入走标准协议，不绑宿主**。用 MCP 把能力暴露出去，任何支持 MCP 的客户端都能接。这样换工具不等于换记忆。

## 代价我也说清楚

本地优先不是白拿的，它有三笔账：

| 代价 | 我的现状 |
|---|---|
| **多设备同步麻烦** | 目前基本没做。换机器靠手动备份文件组（还得注意别拷一半就断电，会坏库）。这是最大的缺口。 |
| **备份得自己管** | 有冷备份流程 + 每日治理脚本，但依赖我自己的纪律，不是产品能力。 |
| **没有云端的便利** | 没有跨设备实时同步、没有团队共享、没有手机端。想用只能在跑服务的那台机器上。 |
| **性能自己扛** | 本地嵌入模型（1024 维）跑在 CPU 上，实测约 1.4 条/秒。库大了必须换策略。 |

我不觉得这些代价可以忽略。它们是真的不便。

## 但我认为这笔交易值得

因为「便利」和「所有权」在这里不是等价的：

- 便利可以后补——同步机制、备份工具、手机端，都是工程问题，可以慢慢做
- 所有权丢了很难拿回来——数据在别人库里、格式是私有的，你连谈判的筹码都没有

而且有一点很关键：**记忆的价值随时间增长，所以它的可迁移性比它当下的便利更重要。**

一个用了三年的记忆库，如果换不了机器，那它的价值就被锁死在那台机器上。

## 我还在解的问题

1. **多设备怎么办**：现在的想法是「本地为源，远端为副本」——但冲突怎么解？两个设备都改了同一条事实，谁赢？版本链能不能做分布式？这块我还没有答案。
2. **跨人怎么共享**：记忆包能做只读传递（我把我的经验打包给你，你挑着入籍），但双向协作没有解。
3. **隐私边界在哪**：现在靠敏感扫描拦密钥，但「公司内部信息」这种语义判断，正则拦不住。要不要做分级？分级之后谁来定级？

这些问题我会一个个试。本地优先不是终局答案，它只是我认为**起点必须站对**的那一步：起点在自己手里，后面的选择才都是自己的选择。
