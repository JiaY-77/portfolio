## 一、立项背景

在使用 AI 编程助手的实际工作中，一个反复出现的问题是**会话状态不可延续**：每次新建对话，都需要重新交代项目背景、协作偏好与任务进度。主流 Agent 产品的能力演进集中在模型能力、工具调用与上下文长度上，**跨会话的记忆能力缺少系统性方案**。

Palimpsest 的项目目标，是补上这一层：**为 Agent 提供一个本地优先、可治理、宿主无关的记忆层**。

立项前，先对现有 Agent 与记忆方案做了两轮调研。

## 二、调研一：主流 Agent 的记忆实现

逐个核查五类代表性 Agent 的架构与记忆机制（结论均来自官方仓库 / 文档，查询时间 2026-10）：

| Agent（开发者） | 定位与特点 | 开源 | 记忆形态 |
|---|---|---|---|
| **Codex**（OpenAI） | 编码专用 Agent；CLI 本地运行 + 云端沙箱并行 | CLI 开源（Apache-2.0，Rust）；云版闭源 | `AGENTS.md`（手写规则，分层合并）+ `~/.codex/memories/`（后台自动摘要，纯 Markdown） |
| **Claude Code**（Anthropic） | 终端编码 Agent；具备 Computer Use（操控桌面）与完整插件体系（skills / subagents / hooks / MCP） | 仓库公开但**无 license 文件**（非标准开源）；沙箱运行时开源 preview | 4 层 `CLAUDE.md`（拼接而非覆盖）+ Auto Memory（`MEMORY.md` 索引，200 行 / 25KB 上限） |
| **OpenClaw**（OpenClaw Foundation） | 本地优先的私人助理；状态/记忆/凭证全在自有硬件，模型与 harness 可换插件 | 开源（MIT，TypeScript） | 五层文件（Instructions / Curated core / Episodic / Prospective / Review）+ 一个 SQLite 索引，后台「Dreaming」晋升 |
| **nanobot**（港大 HKUDS） | 超轻量自托管框架；「记忆应像活的，但不该混乱」 | 开源（MIT，Python） | `SOUL.md` + `USER.md` + `MEMORY.md` + `history.jsonl`；无向量库，检索靠 grep/jq；Git 版本化 |
| **Hermes Agent**（Nous Research） | 自进化 Agent；内置学习闭环（从经验创建技能、跨会话沉淀） | 开源（MIT，Python） | `MEMORY.md`(2200 字符) + `USER.md`(1375 字符) 常驻 + 技能（过程记忆）+ 会话全文检索；可挂外部记忆 provider |

**核查结论**：

1. **形态与定位分化**——五家产品定位差异明显：Codex（OpenAI）以 CLI 为主、兼有云沙箱，是"编码专用"型；Claude Code（Anthropic）以终端 CLI 为主，具备 Computer Use（可直接操控桌面）与完整插件体系；OpenClaw 定位"本地优先的私人助理"，由独立基金会治理、模型与 harness 均可替换；nanobot（港大 HKUDS）为"超轻量自托管框架"；Hermes（Nous Research）主打"自进化"与内置学习闭环。
2. **记忆以纯文件为主**——五家均以 Markdown 承载记忆，向量检索未成为标配（nanobot 的检索依赖 grep）。
3. **记忆与宿主绑定**——`AGENTS.md` / `CLAUDE.md` 面向"本项目的代码修改约定"，属于指令层，不是可跨 Agent 复用的知识层。
4. **缺少冲突消解与版本链**——实现上分为两类：覆盖式更新（Codex 合并摘要、Claude Code Dreams 清理矛盾、OpenClaw 以 supersession key 取代旧观察）与纯追加（nanobot 的 `history.jsonl`）；均无"新事实覆盖旧事实、旧迹可回溯"的版本链。
5. **分层依赖固定预算**——都采用"指令 / 常驻 / 情景"分层，但以上下文预算硬控（2200 / 1375 字符、200 行 / 25KB），检索质量无量化评测。

**选型判断**：五家产品定位不同——Codex / Claude Code 聚焦编码场景，OpenClaw / nanobot 强调轻量自托管，**Hermes 是唯一将"自我改进的学习闭环"作为核心特性**的（从经验自动创建技能、在使用中迭代、跨会话沉淀）。而它的记忆层恰好是最薄的一环（两个小容量常驻文件 + 可外挂 provider）。**"能力最强的地方 + 缺口最明确的地方"正是改造的合适入口**——这构成了下一节的选型依据。

## 三、调研二：独立记忆方案

针对专门做"记忆"的独立方案，核查四个主流实现：

| 方案 | 记忆模型 | 部署形态 |
|---|---|---|
| **Mem0** | 向量 + 图 + KV 三存储并行；LLM 提取事实、去重、更新 | 可自托管，但**自托管栈 = 三容器**（FastAPI + pgvector + Neo4j），默认还调云端 LLM |
| **Letta**（前 MemGPT） | 核心记忆块（agent 自编辑）+ 归档记忆；"LLM as OS"范式 | 可自托管，但它是**整个 Agent 运行时**，不是轻量记忆层 |
| **Cognee** | 关系库 + 向量 + 图；`remember/recall/improve/forget` | 可自托管，以**服务端知识图谱**为核心 |
| **Zep / Graphiti** | 双时间知识图谱（事实失效而非删除）；Graphiti 是开源引擎 | ⚠️ **Zep Community Edition 已于 2025 年 4 月弃用**，只能自托管 Graphiti 引擎，还需外挂 Neo4j 等图库 |

**共同点**：以上方案均以服务端 / 云端架构为中心；即便支持自托管，也普遍是多组件的重量级依赖栈。

**两轮调研定位出的空白**——以下四个条件**需同时满足**，而现有方案均不完整：

> **单机嵌入式（本地优先） + 混合检索 + 冲突消解 / 版本链 + 宿主无关（可接任意 Agent）**

## 四、实证核查：本地跑通并定位缺陷

上述两轮调研以**官方仓库与文档**为依据。为避免"只看文档"的偏差，另做了一轮**实证核查**：在**全本地环境**（Ollama 本地模型，无任何外部 API key）实际跑通 Mem0、Cognee 两家可本地部署的方案，并对读源码定位到的问题做最小复现。

### 4.1 核查方法与范围

| 项 | 做法 |
|---|---|
| 环境 | 全本地：Ollama `qwen3-embedding:0.6b`（1024 维）+ `qwen2.5:3b`，本地 Qdrant / Ladybug 图库，**不依赖云端 key** |
| 范围 | Mem0 2.2.1、Cognee 1.6.3 **实际跑通**（add / search / get_all、add / cognify / search）；Letta 与 Zep/Graphiti 因需外部运行时或图库，做源码级核查 |
| 产出 | 每个问题均给出**可复跑脚本 + 真实报错 + 源码定位**，而非仅描述现象 |

### 4.2 定位到的两个真实缺陷

本轮核查定位到两个可稳定复现的上游缺陷（**完整现象、报错、源码定位与对照实验见姊妹篇《AI 记忆系统的设计与取舍》第三节**，此处只记结论）：

| # | 缺陷 | 一句话结论 |
|---|---|---|
| ① | **Cognee：非 ASCII（中文）用户目录导致开箱即崩** | 报错为误导性的 "Access is denied"，实为**路径编码**问题（其依赖的图引擎在 Windows 下未按 Unicode 处理路径）；已用**纯 ASCII 路径对照组**确认。 |
| ② | **Mem0：embedding 维度硬编码导致的配置断裂** | `embedding_model_dims` 默认值硬编码 `1536` 覆盖 15+ 个向量库实现；embedder 与向量库**各自初始化、维度无同步**，默认值不一致时**静默失败**（错误在写入时才暴露）。 |

**这两个缺陷对设计的直接启示**（已反映到 Palimpsest 的设计里）：

- ① → **本地优先路线中，路径与编码健壮性是真实工程问题**，不能假定运行环境是"干净的 ASCII"。
- ② → **配置一致性应由系统保证**，不应依赖使用者重复声明；维度这类关键参数须**集中管理 + 初始化时断言**。

### 4.3 核查结论

| 缺陷 | 上游状态（查询时间 2026-10） | 对设计的意义 |
|---|---|---|
| Cognee 非 ASCII 路径 | 已在**主分支修复**（2026-10-08，修复说明明确提及 CJK 路径），但**尚未进入任何正式发布版** | 印证"本地优先"路线中**路径健壮性**是真实工程问题 |
| Mem0 维度硬编码 | 官方已有同类报告并标记为**不处理**（`NOT_PLANNED`）——立场是"由使用者显式配置维度" | 印证**配置一致性应由系统保证**，不应依赖使用者重复声明 |

**这一轮核查的价值，在于两点判断：**

1. **缺陷定位能力**：两个问题都做到了"从现象 → 最小复现 → 源码定位"的完整闭环，而非停留在报告层面。
2. **上游判断力**：核查上游状态后确认——**两个问题均不适合再提交补丁**（一个已修、一个被官方认定为设计选择）。因此**主动放弃**提交，避免与既有工作重复。**判断"什么不该做"，与找到"什么该做"同样重要。**（该判断的完整依据见姊妹篇第六、七节）

> **本节的执行说明**：核查方法、范围与结论判定由本人确定；具体实测脚本编写、环境搭建与源码走读由 AI 编程助手执行，本人负责验收结论并决定是否对外提交。

### 4.4 对 Palimpsest 的落地

上述调研不止于结论，其中可借鉴的设计已在项目中落地实施（详见第五节设计决策与版本记录）：

- **时间维度**（借鉴 Graphiti 的双时间知识图谱）→ 已实现事实的有效时间与失效时间字段、历史时点视图、基于时间窗的冲突判定
- **写入口约束**（借鉴 Letta 的提交前校验）→ 已实现写入入口的策略护栏（只读节点保护、分级上限、配置变更人工闸门），默认预警模式
- **维度一致性** → 已实现维度一致性检查项（`doctor` 自检，校验索引维度和存储维度是否匹配），把问题暴露在自检阶段而非等到写入失败

## 五、架构选型：以 Hermes 为基座

五类 Agent 中，选 **Hermes Agent（Nous Research，MIT 开源）** 作为基座，依据是需求匹配度：

1. **具备学习闭环**——可从经验中自动创建技能、在使用中迭代、跨会话沉淀。
2. **记忆层可替换**——内置记忆为两个小容量常驻文件（`MEMORY.md` 2200 字符 + `USER.md` 1375 字符，每轮全量注入），并支持外挂记忆 provider。这一层即为改造入口。
3. **MIT 协议、完全开源**——可自由修改与分发。

选型逻辑：Hermes 的自进化机制解决"会不会学"，记忆层解决"记不记得住"。**在其上补齐一个本地可控的记忆层，即可实现跨会话的能力延续。**

## 六、Palimpsest 与主流方案的异同

需要区分两件事：**项目的设计来源**与**本次调研的作用**。

**设计来源**：

1. **起点是既有需求**——此前为解决"酒馆对话上下文溢出"开发了本地记忆原型 **MemoryHub**，Palimpsest 由此重构而来。
2. **同期参考**——在深化过程中，研究过 **pi-hermes-memory**、**memorix** 等"编码 agent 记忆层"项目，参考了其中的自动学习循环、preview-first 治理、Git 记忆等具体做法。
3. **核心设计为独立推导**——混合检索、记忆分层、图谱关联、版本链等，是在解决自身问题的过程中逐步确定的方案。

**本次调研的作用是事后对照**：将已实现的系统与主流方案逐项比对，得到两点结论：

- **设计方向与主流方案一致**——Mem0 的混合存储、Letta 的分层、Cognee 的图持久化，与 Palimpsest 已采用的技术方向重合，验证了架构方向。
- **差异点成立**——主流方案多为"服务端 / 云 + 多组件栈"，而 Palimpsest 为单机嵌入式、本地优先、自带治理。**四条件同时满足者目前尚无。**

### 差异化设计：策略引擎与宿主无关协议

在确定"记忆层独立于宿主"这一方向时，参考了几项同期的工作与标准进展：

- **Letta《Why Memory Isn't a Plugin》**——论证上下文与状态管理是 agent harness 的核心职责，无法以插件形式外挂。这支持了"记忆智能不应寄居在宿主插件接口内"的判断。
- **Jev-Mem**（arXiv 2609.23986）——以 System-1 / System-2 双层控制 agentic memory，用轻量结构化预测处理高频记忆操作，重型 LLM 仅用于最终推理。这与"记忆的判定逻辑应自成引擎"的取向一致。
- **MCP 2026-07-28 协议修订**——移除 server-initiated sampling，改为多轮往返请求（MRTR）。说明宿主侧钩子的能力边界在收缩，记忆的生命周期能力更应通过**宿主无关的通用协议**暴露。

**落地（v2.5.0）**：将"什么值得记、记哪一层、何时召回、怎么去重"的判定从宿主插件收进本体 `core/strategy.py`，并暴露一组宿主无关的 lifecycle 端点（`pre-turn` / `post-turn` / `session-end` / `pre-compress`），每个决策返回 `decision_log` 使判断可审计；宿主适配器压薄为纯传输层，不再包含任何阈值与正则。

### 核心设计决策

| 决策 | 做法 | 依据 |
|---|---|---|
| **本地优先** | 单进程嵌入式存储，进程内读写，零运维 | 数据完全本地，不依赖服务端；离线可用 |
| **混合检索** | 语义向量 + FTS5 全文 + 图谱扩散，RRF 融合排序 | 语义匹配与精确查询互补，单一方式均有盲区 |
| **记忆治理** | 冲突检测分级 + `REVISED_BY` 版本链 + 相似合并 + 记忆分层 | 实现"覆而不失、改写可溯"：新事实取代旧事实，旧迹可回溯 |
| **本地知识库接入** | 扫描 Obsidian vault（`.md`），按标题切片（300~800 字符）向量化入库，支持增量更新与索引规则配置 | 复用用户已有的本地笔记资产，不要求迁移格式 |
| **宿主无关** | 从 Hermes 插件下沉为独立核心，暴露 lifecycle 协议 | 不限定单一宿主，任意 Agent 均可接入 |

**命名**：Palimpsest（重写本）——原指被反复覆写、旧字迹仍可辨认的羊皮纸。命名对应系统的核心语义：**新事实覆盖旧事实，旧迹不丢失**。

## 七、本地知识库接入

除对话记忆外，Palimpsest 的另一条主要路径是**接入本地已有的 Markdown 知识库**（典型场景为 Obsidian vault）。数据不迁移、不改格式，直接对 vault 目录建索引：

- **扫描与切片**：递归扫描 vault 内 `.md` 文件（默认跳过 `.obsidian`），按 Markdown 二 / 三级标题切片，每块 300~800 字符
- **向量化入库**：切片以 `kb_chunk` 节点写入本地库，与记忆节点共用同一套检索通道
- **增量更新**：以源文件 mtime 判断变更，仅重建新增或修改的文件，未变文件跳过；重建采用 upsert 策略保持节点 id，**图谱关联不因重建丢失**
- **规则可配置**：支持 vault 级索引规则文件，自定义切片策略与排除目录；文档生命周期同样被管理——引言区标记为"已退役"的文档不进入索引，其历史切片同步清理

**设计依据**：本地 Markdown 是既有的个人知识载体，格式稳定、可版本控制、可离线阅读。让记忆系统直接消费这一类资产，而非要求用户迁入新格式，是"本地优先"在数据层面的延伸。

## 八、近期演进：从「记得住」到「记得对、传得走」（v2.11 – v2.14）

记忆系统真正的难点不在「存下来」，而在两个更晚才浮现的问题：**写进来的东西可不可信**、**记忆能不能离开这台机器**。2026 年 10 月的四个版本都在处理这两件事。

### 8.1 记忆包：让记忆可以流转（v2.11）

新增一种自包含的 JSON 记忆包，支持**导出 / 只读解开 / 挑着入籍**三件事：

- **只读解开**（`mem_unpack`）：不写库、不开事务，先校验格式与版本、扫描敏感信息、给人一份可读摘要 —— 「先当故事听」
- **挑着入籍**（`mem_import`）：先返回可选清单，人选定哪些再写回本库 —— 不做「整包导入」这种不可逆动作
- **写入判定观测**：每次写入后把判定计数（相关命中 / 显式取代 / 标为过期）追加到同目录的观测文件，`mem_stats` 按 30 天窗汇总。**观测数据只记计数与元信息，不含记忆正文、不进检索池、不建节点** —— 目的是回答「写入方到底有没有做写入前判定」，而不是再存一份副本。

设计取舍：跨实例流转的最大风险不是格式，而是**「把别人的记忆当成事实」**。所以流转的默认动作是「读」，写入必须由人挑选。

### 8.2 思维预设层：让「思考」成为可检索的一等公民（v2.12）

宿主每轮模型调用前，向本体取一份**思考骨架**（按任务类型给不同的结构引导），拼进 prompt；回合结束后，本体把正文里的 `<thought>...</thought>` 段抽出来落库。

两个设计决定值得说明：

- **不依赖任何模型的原生 CoT 字段**：思考写在正文里，所有模型通用；换模型不用改接入
- **宿主与本体分工**：宿主只负责「取骨架、包成指令、把思考还回来」，判断与落库全在本体；插件是纯传输层

诚实边界也写进了实现：宿主无法区分「骨架引导出的产物」与「模型原生思考」，所以落库时打两个互补字段——一个是宿主上报的**事实字段**（本轮注入了哪种骨架），一个是本体按文本起手式判定的**启发式字段**（长得像不像）。两者不一致，就能查出「注入了骨架但模型没照写」；单独任何一个都不声称精确归因。

### 8.3 在真实宿主里跑通，才算设计成立（v2.13）

这一版修的几乎全是「在真实宿主里静默失效」的问题 —— 测试全绿、但功能实际从未生效：

- 插件被宿主**加载两次**，初始化只调用了其中一个实例 → 注入闸门恒为关闭，骨架永远不注入
- 收侧只取「最后一条」assistant 消息的思考，而一个回合里有工具循环、多条 assistant 消息，写思考的往往不是最后那条 → 整轮思考被丢弃

两个问题都补了回归测试。此外还加了两处**宁可拒绝也不静默降级**的护栏：超长 query 直接 422（不静默截断）；embedding 失败与「确实没有结果」必须区分（前者 503 / 422 上报，后者才返回空结果 + 程序可读的降级标记）。

**这条经验比代码本身更重要**：在测试环境里「功能全绿」，不等于在真实宿主里「功能生效」——集成点的状态机必须用生产形态验证。

### 8.4 活跃任务：让「老任务自己退场」（v2.14）

任务列表在长期使用后会变成僵尸场：建了很久、再没动过的任务一直排在前面。这一版加了三个机制：

- **新鲜度维度**（`fresh_days`，默认 30 天）：判据取「最后触碰时间」与「创建时间」的**更早者** —— 因为存量任务的最后触碰时间会被批量回填刷成同一天，单看它会让建了半年的老任务显示成「刚动过」而永不退场
- **接续点置顶**：跨会话交接条目按重要性排在普通任务之前，并豁免新鲜度折叠（交接信息不该被「旧」掉）
- **治理哨兵自动降级**：`doing` / `blocked` 超 30 天未动 → 自动标为待复核并写一条可回溯的日志；超 60 天**只输出归档建议清单，不执行删除** —— 删除权始终留给人
