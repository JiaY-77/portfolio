## 一、问题的起点：为什么「问它你是谁」没有用

大模型 API 聚合市场（俗称「中转站」）存在一类常见问题：**标称的模型与实际提供的不一致**。表现形式包括参数名对不上、模型版本降级、同名模型背后挂多渠道随机路由等。

一个直觉做法是直接问模型「你是谁」。**这个做法必然失败**，原因是：

> **模型的自我认知来自「上下文」，而不是「训练」。**

中转服务可以在请求里注入 system prompt 或配置，把「你是某某型号」写进去。模型会照着念——它的回答反映的是**本次对话告诉它什么**，而不是**它训练时学到了什么**。

这一点决定了鉴别方法的走向：**不能问身份，只能测行为。**

## 二、鉴别方法（五个层次，由硬到软）

### 2.1 上游结构指纹（最硬的证据）

走原生端点发起请求，观察**响应结构**——这部分通常由上游厂商的 API 决定，中转方难以伪装：

| 观察项 | 判据 |
|---|---|
| 响应体 `id` 前缀 | `msg_bdrk_...` = AWS Bedrock 上游；`msg_011C...`（无 bdrk）= 厂商官方直连 |
| `usage` 字段构成 | 出现 `inference_geo` / `service_tier` / `output_tokens_details` = 较新的官方 API 结构；只有 `cache_creation` 等字段 = 较早期的结构 |
| 响应头 | 可暴露中转服务自身的版本信息 |

**为什么最硬**：这些字段由上游生成，中转方要改就得自己重写响应体，成本与风险都高。

### 2.2 知识截止期探针

**问它知不知道「某时间点之后才发布的东西」**——真实模型的知识窗口藏不住。

示例问法：

```
请按顺序列出你知道的 <某模型家族> 所有版本及发布时间，从第一代到最新。
```

把它的回答与**真实发布日期表**对照。判定：

- 若它自称是某新版本，却不知道该版本之前就已发布的型号 → **参数名与实际不符**
- 若它把已知的发布时间说成「未来」→ 它的知识窗口早于该时间点

### 2.3 决定性探针：区分「训练知识」与「上下文注入」

这是整套方法里最关键的一步。既然身份可以注入，就要**逼模型自己交代出处**：

| 问法 | 效果 |
|---|---|
| ❌「你是谁」/「最新版是什么」/「世界上存在哪些版本」 | 它念配置，会被骗 |
| ✅「**你确定存在的最新版本是什么？这个信息来自哪？**」 | 逼它交代来源——它可能自己承认「本次会话的配置告诉我……」 |
| ✅「**哪些是你训练学到的，哪些是配置或上下文告诉你的？**」 | 逼它分离两个来源 |
| ✅「**你实际知道的最新版本是什么（不要用当前对话的信息）**」 | 直击真实知识边界 |

**判定法**：

- 问「**你实际知道的**」→ 得到**真实知识边界**
- 问「**世界上最新的**」→ 得到**注入的剧本**
- 两者不一致 = **身份注入确认**

探针模板（可直接复用）：

```
For each item answer KNOW (from your training) or UNKNOWN, and if KNOW give one fact:
(a) <版本 A>  (b) <版本 B>  (c) <版本 C>
(d) <版本 D>  (e) <近期事件 1>  (f) <近期事件 2>
Be rigorous: only say KNOW if genuinely in training, not from this conversation's context.
```

真模型会给出与自身版本一致的知识窗口；注入模型会「前面 KNOW 到某一代、后面全 UNKNOWN」，与它自称的版本自相矛盾。

### 2.4 路由漂移检测

**同一个短请求连跑数次，观察 `prompt_tokens`**：

| 现象 | 含义 |
|---|---|
| 稳定（如每次都是 4） | 单一渠道 |
| 剧烈跳动（如 4 / 346 / 18912） | 同名模型背后挂**多渠道随机路由**，质量不可控 |

另一个信号：**极短请求却带巨大 `input_tokens`**（如 1.8 万）——说明请求被套上了一层「官方客户端系统提示信封」，通常意味着后端是**订阅逆向**（把订阅账号反代成 API），而非官方裸 API（后者的 `input_tokens` 通常只有个位数）。

### 2.5 真实单价实测

站点公示的价格可能滞后或被修饰，**以实测为准**：

1. 先确认无其它调用（记录 `total_usage` 基线）
2. 发两个**输入量差异大**的请求（如 200 遍重复词 vs 400 遍）
3. 记录每次的 `prompt_tokens` 与额度增量，解方程求出「每输入 token 额度」和「每输出 token 额度」

**健全性检查（关键）**：

- 求出的 `输出单价 / 输入单价` 应接近该模型公示的 `completion_ratio`（常见 4~5）。**不符 = 数据有噪声，重测**
- 用两轮独立数据推算的「额度 → 金额」汇率应当一致（实践中的一次实测：1440 vs 1436，差异在噪声范围内）——**一致才可信**

**为什么必须用大请求**：小请求的额度增量太容易被噪声淹没，会解出无意义的负值。

## 三、实践案例（已脱敏）

### 案例：识别「身份注入」的套壳

**现象**：某服务商标称提供某模型家族的新版本，参数名也用了新版本命名。

**过程**：

1. 直接问身份 → 模型自称是该新版本，并给出「知识截止 2026-06」
2. 换用 2.3 的决定性探针 → 追问「你确定存在的最新版本是什么、这个信息来自哪」
3. 模型承认该结论**来自本次会话的配置**，而非自身训练
4. 用版本-日期对照表逐项验证 → **真实训练知识停在 2025 年底**：它知道较早期的型号，但对之后的数个版本全部答 UNKNOWN

**判定**：参数名标称的新版本与真实知识窗口矛盾，且自我认知可被证实来自上下文注入 → **旧模型 + 身份注入**。

**意义**：这个案例说明「模型自报身份」作为证据的不可靠性，以及行为探针的必要性。

## 四、可复用的检查清单

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 上游 `id` 前缀与 `usage` 结构 | 与标称厂商的原生结构一致 |
| 2 | 知识截止期 | 与标称版本的发布时间自洽 |
| 3 | 训练知识 vs 上下文注入探针 | 两者一致（无注入） |
| 4 | 同请求多次的 `prompt_tokens` | 稳定（单渠道） |
| 5 | 极短请求的输入量 | 正常（无订阅逆向信封） |
| 6 | 实测单价与公示倍率 | 交叉验证一致 |

**把这六项串起来，就是一套不依赖「问身份」的鉴别流程。**

## 五、边界与已知限制

1. **依赖版本-日期对照表**：2.2 与 2.3 的判据需要维护「型号 ↔ 真实发布时间」，表过期就会误判。
2. **注入方也在进化**：本文的方法是 2026 年的实践；对抗手段会变化，方法需要持续更新。
3. **单一信号不足**：任何一层单独看都可能误导，实践中应当**多层交叉**再下结论。
4. **只做行为观测**：本文方法不涉及逆向、破解或绕过任何服务方限制。
5. **方法已沉淀为可复用流程**：不是一次性测试，而是可重复执行的检查清单（见第四节）。
