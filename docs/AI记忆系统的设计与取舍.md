## 写在前面

我不是算法研究者，也不是资深工程师。我的角色是**产品定义者与设计者**——发现问题、定义方案、做技术取舍、验收成果，编码由 AI 编程助手按需求协作实现。

过去一年，我为自己做了一个 AI 记忆系统（Palimpsest），并沿着这个方向做了大量竞品实测与源码走读。本文记录我在这条路上的**观察、对比与判断**——包括一个我认为比"做了什么"更重要的问题：**什么不值得做。**

---

## 一、我为什么关注"记忆"

AI 助手有个被普遍忽视的问题：**它记不住。**

不是"上下文不够长"的问题——上下文可以塞到百万 token，但**会话一结束，一切归零**。下次对话，它不认识你，不记得上周定过什么方案，也不知道你已经在某个问题上绕了三圈。

这引出了一串真问题：

- **什么值得记？** 不是所有对话都值得，全存下来等于没存。
- **新旧冲突怎么办？** 用户换了工作，新事实进来，旧的要删吗？删了历史就断了。
- **怎么想起来？** 存了 1000 条，用户一句话，怎么把**对的那条**捞出来？
- **怎么知道它没记坏？** 记忆系统最难的不是写，是**知道自己退化没有**。

我给自己的答案是「**覆而不失、改写可溯**」：新事实覆盖旧事实，但旧事实通过版本链可追溯，让事实的演化过程可见。这个模型我想了很久，也是 Palimpsest 的设计原点。

## 二、主流方案实测：它们各自牺牲了什么

### 2.1 跑通状态总览

| 方案 | 版本 | 状态 | 本地依赖 |
|---|---|---|---|
| **Mem0** | 2.2.1 | ✅ 跑通（`add` / `search` / `get_all`） | Ollama + 本地 Qdrant |
| **Cognee** | 1.6.3 | ✅ 跑通（`add` / `cognify` / `search`） | Ollama + 本地 Ladybug 图库 |
| **Letta** | `letta-code`（TS） | 源码级核查 | 需 Docker，本机未跑 |
| **Zep / Graphiti** | Python | 源码级核查 | 需外部图库，本机未跑 |

**共同前提**：无外部 API key，全部走本地 Ollama。
**一个实测坑**：Ollama 必须使用**专用 embedding 模型**；用对话模型去 embed 会返回 501。
**一个事实修正**：Letta 已重构——`letta-ai/letta`（Python）主分支只剩文档，当前源码在 **`letta-ai/letta-code`（TypeScript）**。旧调研中"Docker 自托管 Postgres"的描述已过时。

### 2.2 同一个"记住事实"，设计哲学完全不同

| 方案 | 记忆模型 | 它牺牲了什么 |
|---|---|---|
| **Mem0** | 事实抽取 + 向量检索 | **不带时间维度**——只记"现在是什么"，不记"什么时候变成这样的" |
| **Graphiti** | 双时间字段（`valid_at`/`invalid_at`）+ 知识图谱 | 复杂度高、依赖外部图库 |
| **Letta** | 分层记忆（核心/归档）+ 自编辑 | 偏 agent 运行时，独立使用门槛高 |
| **Cognee** | 显式分阶段管线（抽取→建图→检索） | 管线重，跑起来成本高 |

**这个表本身就是我的技术判断来源**：没有"最好的方案"，只有"为哪个问题做的取舍"。

## 三、我实测暴露的两个真实缺陷（含源码定位）

### 缺陷一：Cognee 在中文用户名下开箱即崩

**现象**（Windows 中文用户名 `C:\Users\<中文用户名>\`）：

```
RuntimeError: IO exception: Cannot open file.
path: C:\Users\<中文用户名>\AppData\Local\Temp\...\graph.lbug
- Error 3: The system cannot find the path specified.
```

并伴随一条**误导性日志**：

```
Failed to create directory C:\Users\<中文用户名>/.lbdb/extension/0.19.0/win_amd64/
... error message: Access is denied.
```

报"拒绝访问"，实际是**路径编码**问题——这条日志会把人引向权限排查的错误方向。

**对照实验**（同一份代码，只换路径）：

| 路径 | 结果 |
|---|---|
| `C:\lbg_pure_ascii_test\`（纯 ASCII） | ✅ 成功 |
| `C:\Users\<中文用户名>\...`（含中文） | ❌ 失败 |

**源码定位**（读其依赖的 `ladybug` 图引擎源码）：

1. `src/main/client_context.cpp` → `getUserHomeDir()`：Windows 分支取 `USERPROFILE`，即 `C:\Users\<中文用户名>`
2. 同文件 → `getExtensionDir()`：拼出 `{home}/.lbdb/extension/{version}/{platform}/`
3. `src/common/file_system/local_file_system.cpp` → `createDir()`：经 `toNativePath()` 落到文件系统层，**未按 Unicode 处理路径**

**上游状态（我核查了）**：该问题**已于 2026-10-08 在主分支修复**（提交说明明确提及 CJK 路径），但**尚未进入任何正式发布版**（最新 release 早于修复）。

**结论：不提 PR**（上游已修，重复）。可考虑提 issue 询问是否 backport 到发布线。

### 缺陷二：Mem0 的 embedding 维度硬编码

**现象**（只配置 embedder 维度、不重复配置向量库维度）：

```python
ValueError: Wrong input: Vector dimension error: expected dim: 1536, got 1024 for vector ''
```

错误抛在底层向量库（`qdrant_client`），**不指向 mem0 的配置根因**。

**源码定位**：

1. `mem0/configs/vector_stores/*.py`：`embedding_model_dims` 默认值硬编码为 `1536`，覆盖 15+ 个向量库实现
2. `mem0/utils/factory.py`：`EmbedderFactory.create()` 接收了向量库配置，但**除一个特例外未被使用**；而 `mem0/memory/main.py` 里的 `VectorStoreFactory.create()` **只能拿到向量库自己的配置**，无从获知 embedder 实际维度

**因果链**：两个组件各自初始化 → 维度无同步 → 默认值不一致时**静默失败**（错误在写入时才暴露）。

**上游状态**：官方已将该问题 **CLOSED / `NOT_PLANNED`**（2026-04），维护者立场是"**由使用者显式配置维度**"，属设计选择。另有 issue 与其 PR 处理的是**另一个子问题**（已存在的 collection 维度不匹配时不报错），且只覆盖单个向量库实现，已搁置。

**结论：不提 PR**（官方立场已明确）。

## 四、值得借鉴的设计（按价值排序）

| # | 来源 | 设计点 | 对自研系统的意义 |
|---|---|---|---|
| 1 | **Letta** | 提交前约束校验（单文件 / 核心 / glob / 深度 / 只读保护 + 分级上限 + 配置改动需人工批准） | 写入入口可加"校验 + 阈值闸门"，防自动化流程自己放开限制 |
| 2 | **Graphiti** | 双时间字段（`valid_at` / `invalid_at` / `expired_at` / `reference_time`）+ 反向索引 | 只记"写入时间"无法回答"三个月前它认为这条是什么" |
| 3 | **Graphiti** | 冲突判定的时间窗逻辑：时间窗不重叠就不算矛盾（"十年前住北京" ≠ "现在住上海"） | 纯语义相似度判定会产生误报 |
| 4 | **Letta** | compare-and-set + token + 仅回收死进程的锁 | 多 agent 并发写的防错范式 |
| 5 | **Cognee** | 显式分阶段管线 + 检索/生成解耦 | 知识库入库可参考"显式分阶段 + 可观测" |
| 6 | **Mem0** | 反面教训：维度散落 20+ 后端硬编码 | 维度集中管理 + 初始化时探测断言 |

**其中两条我直接借鉴到了自己的系统里：**

- **双时间**：每条事实记两个时间——"它什么时候为真"和"我什么时候知道的"。**只记写入时间，无法回答"三个月前我认为这条是什么"**。
- **时间窗冲突判定**：两条事实时间窗不重叠就不算矛盾。**这个设计直接减少了误报。**

## 五、已落地的改进

上述借鉴项已在自研系统中实施（均有公开提交记录）：

- **时间维度**（借鉴 #2/#3）→ 事实的有效/失效时间字段、历史时点视图查询、基于时间窗的冲突判定
- **写入口约束**（借鉴 #1）→ 策略护栏：只读节点保护、按类型分级上限、配置变更人工闸门（默认预警模式）
- **维度一致性**（借鉴 #6）→ 自检项校验索引维度与存储维度是否匹配

## 六、我认为最值得说的一件事：什么不该做

以上两个缺陷，都**看起来是很好的"开源贡献机会"**：
- 都是真实的、可复现的 bug
- 都有清晰的根因定位
- 提了 PR 就能写进简历"我为 XX 项目贡献过"

**但我都决定不提。** 理由：

1. **一个上游已经在 3 天前修了**——再提就是重复劳动、消耗维护者时间
2. **另一个官方已明确表态不打算改**——立场清楚，提了也会被关

**我的判断标准是：提上游不是"刷简历"，是"给维护者提供价值"。** 如果这件事对项目没有净增益，那"我提过一个 PR"这个标签，价值是负的——它浪费了别人的时间，也说明我没做功课。

**我认为这个判断本身，比那两个 bug 更有价值。**

## 七、方法论：我提上游前会做三件事

写在这里，供参考，也供自我检查：

1. **搜现象描述，不只搜 API 名**——"hardcoded 1536"、"not propagated" 这类描述，比关键词更容易找到已有讨论
2. **看 issue 的 `stateReason`**——`NOT_PLANNED` / `wontfix` 意味着官方立场已定，不用再试
3. **查修复是否已进 release**——看主分支有没有修（`git log -S <符号>`），再比对 release tag 日期。**主分支修了但没发版**，是很容易踩的坑

**以及一条更基础的**：路径类问题，**先设纯 ASCII 对照组**。Cognee 那个"拒绝访问"如果只做权限排查，会走进死胡同。

## 八、我对自己系统的反思（诚实版）

写这份文档时，我也发现了自己系统的不足：

**我的图谱曾经很稀疏**——60.6% 的节点没有任何边，检索只能靠向量和全文。最近我补齐了结构化建边（六类边源），孤立率降到 16.6%。

**但"图更密"不等于"检索更好"。** 我的评测数据显示，某些场景下检索提升并不显著——**指标变好和体验变好，是两回事**。这是我下一步要搞清楚的问题。

**以及一个更尴尬的发现**：我的评测集本身失效了——答案的节点 ID 在库重建后全部对不上，等于**拿错答案在评分**。修正之后，我才拿到真实的数字。

**这件事让我明白：先有可信的尺子，才谈得上改进。**

## 九、我的判断

- **记忆是 Agent 的基础设施，不是功能点。** 模型再强，"记不住"这件事不会自己消失——上下文窗口解决不了"跨会话"。
- **时间维度是被低估的设计。** 大多数方案只记"现在是什么"，但"什么时候变成这样的"才是可追溯性的关键。
- **评测比功能难做，也比功能重要。** 一个说得清自己"好在哪、坏在哪"的系统，比一个只会加功能的系统可信。
- **判断"不该做什么"，和判断"该做什么"一样重要。**

这条路我会继续走。不是因为它是风口，是因为我认为这些问题是真问题。
