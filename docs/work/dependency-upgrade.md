# 依赖升级不靠「感觉」：一次存储引擎升级的验证与上游贡献

> 本文记录一次底层存储引擎（TriviumDB 0.8.8 → 0.8.9）升级的完整验证过程，以及由此产生的上游贡献。
> 所有数字均为本机隔离环境实测；涉及上游项目的结论以官方仓库为准。

---

## 一、为什么要花时间验证一个「小版本升级」

新版默认启用了新的向量内核，官方说明里写着「吞吐更高」。但依赖升级的真实风险从来不是「新版更慢」，而是三件更难发现的事：

1. **数据格式变了没有** —— 变了就得迁移，迁移失败就是事故
2. **性能是变好还是变差** —— 官方数字是在他们的硬件、他们的数据上测的
3. **新行为在真实库上是否安全** —— 压测数据往往是合成数据，真实数据分布未必一样

这三件事靠看 changelog 判断不了，只能自己测。

## 二、验证方法：隔离、对照、真实库

| 环节 | 做法 | 为什么 |
|---|---|---|
| 环境隔离 | 两个独立 venv（0.8.8 / 0.8.9），同机同轮 | 避免装包互相污染，保证差异只来自版本 |
| A/B 对照 | 固定 seed 生成等价数据，两版跑同一脚本 | 单版本跑两次的抖动会被误读成版本差异 |
| 规模分层 | 小规模（2000 节点，走精确路径）+ 大规模（20000 节点，触发 ANN） | 两个版本的优化点在不同路径上，只测一种会漏 |
| 真实库冒烟 | 复制真实库文件，用新版打开、检索、核对召回 | 合成数据测不出真实分布下的问题 |
| 升级窗口 | 停服务 → 冷备份（回读校验节点数）→ 升依赖 → 重启 → 端到端冒烟 | 升级本身要可回滚 |

## 三、结果一：零迁移，跨版本打开正常

存储格式的六项版本号（database_format / minimum / property_index / quiver / text / wal / manifest）与旧版完全一致 —— 新库直接打开旧库，**不需要导出重建**。

真实库跨版本打开后检索正确：**2145 节点 / 1024 维 / 6 个属性索引 / 3199 条边，recall@10 = 1.0**。

## 四、结果二：新版更快，但「快在哪」要说清楚

| 指标（1024 维） | 0.8.8 | 0.8.9 | 变化 |
|---|---|---|---|
| 小库（2000 节点）向量检索 QPS | 1575.8 | 1577.9 | 持平 |
| 大库（20000 节点）向量检索 QPS | 667.5 | **1189.3** | **+78%** |
| 无索引 `FIND + LIMIT`（小库） | 26,598 | **66,682** | **2.5×** |
| 无索引 `FIND + LIMIT`（大库） | 4,653 | **44,297** | **9.5×** |
| recall@10（真实分布数据） | 0.965 | **1.0** | 不降反升 |

- 向量检索的 +78% 只在大规模（触发 ANN 路径）时出现；小规模走精确路径，本来就没有优化空间 —— **报「平均提升」会误导**，所以按规模分开列。
- 无索引查询的提升来自另一处修复，与本项目实际用到的接口相关，因此单独列。

## 五、关键发现：一个真实的性能回归，我提给了上游

压测中发现：**无索引的 `FIND + LIMIT` 在 v0.8.8 上掉到了 26,598 QPS（小库）/ 4,653 QPS（大库），而 v0.8.6 是 66,682 QPS** —— 上游 issue 标题里记为「约 28× 慢于 v0.8.6」。成因是执行规划阶段先做了完整的候选物化，再把这些候选丢弃。

处理顺序（先查，后报）：

1. **先确认不是自己用错** —— 同脚本在 0.8.6 / 0.8.8 / 0.8.9 三版对照，确认差异随版本走
2. **再查上游是否已知** —— 读源码定位到执行计划阶段（`memtable` 的候选物化），不是配置问题
3. **然后提 issue + PR** —— [issue #58](https://github.com/YoKONCy/TriviumDB/issues/58)（性能回归说明 + 复现脚本与数据）、[PR #59](https://github.com/YoKONCy/TriviumDB/pull/59)（短路掉无索引路径上的候选物化）
4. **结果**：上游没有直接合并这个 PR，而是以自己的实现（`3a0957a`，保留全部索引路径 + 扫描兜底按需物化 + 计数器）**吸收了同一修复**，并在提交信息中保留了我的共同署名。

> 判断一件事值不值得做，标准不是「我的代码有没有被合并」，而是「问题有没有被解决」。这次问题解决了，署名也留下了，PR 关闭是正常结局。

## 六、一个被我自己撤回的结论：写性能「+29%」

第一次跑压测时，写 1000 条的数据显示 0.8.8 为 0.301 s、0.8.9 为 0.388 s，反向推算「写入慢 29%」。

发出去之前重跑了一次，发现这个数字站不住：

- **单次采样**：同一脚本重跑 3 次，绝对值从 0.18 s 漂到 0.45 s
- **计时口径错误**：计时循环里包含了 1024 维随机向量的**纯 Python 生成**（约占 0.15 s），实际测的是「生成 + 写入」

改成「向量预生成、丢前 2 轮取中位数」后复测：

| 场景 | 0.8.8 | 0.8.9 | 结论 |
|---|---|---|---|
| 纯写路径（2 万节点，无额外索引） | 23.4 ms | 23.9 ms | **+1.9%，噪声内** |
| 带有序索引的写路径 | 254.1 ms | 284.9 ms | 抖动 183–448 ms，差值埋在噪声里 |

**结论撤回：新版稳态写速与旧版持平（±2%），不存在「写入慢 29%」**。这条撤回也写进了验证报告，并存进项目记忆 —— 用来提醒自己：**单次采样 + 计时含数据生成的性能数字，以后不许对外报**。

## 七、第二个否证：合成数据不能用来评估量化索引的召回

为了回答「维度越高是否越难」这个问题，我用「单位球面簇心 + 噪声」的合成数据测了 384 / 768 / 1024 / 1536 / 3072 维的 ANN 召回，结果**毫无规律，且版本之间自相矛盾**（同一维度 0.8.8 得 0.28、0.8.9 得 0.0）。

根因：量化索引用的是 2-bit 符号+强度签名，而合成高斯数据各维近乎同分布、没有稀疏结构 —— 签名抓不到区分度，图导航退化成随机游走（返回点的余弦相似度 ≈ 1/√d，即「不相关」水平）。

**推论**：任何**量化**索引（BQ / PQ / SQ）的召回验证，都必须用**真实分布**数据；合成均匀/高斯数据只能用来测 QPS、内存这类与数据分布无关的指标。

顺带排除了一次「疑似引擎 bug」：合成数据上出现分数异常、间歇返回空列表，换真实数据后全部正常 —— **不是缺陷，是我用错了数据**，因此不报上游。

改用真实向量（真实库 2144 条 1024 维 + 扰动扩充到 8500 节点）后，同样的问题有了明确答案：

| 维度 | 精确检索 QPS | 内存 | 建库 |
|---|---|---|---|
| 384 | 1,149 | 34.9 MB | 1.7 s |
| 768 | 533 | 61.3 MB | 3.3 s |
| 1024 | 396 | 78.6 MB | 4.3 s |
| 1536 | 282 | 113.1 MB | 6.4 s |
| 3072 | 145 | 216.8 MB | 12.4 s |

**维度翻倍 → 精确检索约慢一半、内存翻倍**。这不是「好/坏」，是代价：维度由 embedding 模型决定，换维度等于换模型，所以结论不是「选哪个维度」，而是「知道这个代价，别乱换」。

## 八、这套方法能复用到哪

任何「升级一个底层依赖」的场景都适用：

1. **先问格式兼容**，不兼容的事先算迁移成本与回滚方案
2. **再问性能**，按规模/路径分层测，不要报平均值
3. **别信单次采样**，丢前几轮取中位数，计时范围只包被测逻辑
4. **合成数据只测与分布无关的指标**，召回类验证必须用真实分布
5. **报上游前先自查**，确认不是自己用错、不是已知问题、能用最小复现说明
