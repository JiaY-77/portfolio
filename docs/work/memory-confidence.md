# 记忆置信度：让分数由证据算出来，而不是让人打出来

> 一个记忆系统里，除了「这条重不重要」，还缺一个维度：「这条有多可信」。
> 这篇文章记录我怎么从「主观打分」走到「证据算分」，以及在 2969 条真实记忆上跑出来的结果。

---

## 一、问题：重要 ≠ 可信

记忆系统通常只有一个重要度字段（importance）。但两件事其实正交：

| | 含义 | 例子 |
|---|---|---|
| **重要度** | 这条**多重要** | 「客户可能下周签约」——很重要 |
| **置信度** | 这条**多可信** | 同一句——但只是猜测，可信度低 |

系统把这两件事压成一个维度，后果是：一条「重要的猜测」和一条「重要的确定事实」被同等对待。

---

## 二、第一版方案（以及为什么放弃）

最直觉的做法：让写记忆的那一方给每条记忆打个分，1–5 档。

放弃它有三个理由：

**1. 不可复现。** 同一个模型，两次写同一件事，可能给出不同的分数。置信度如果不可复现，它就不是一个可计算的量。

**2. 档位边界说不清。** 3 分和 4 分的区别是什么？没有硬判据的话，5 档就是 5 个噪声源。**粒度不是精度。**

**3. 判断发生了太多次。** 逐条打分 = 每条记忆一次主观决策。而正确的做法是把判断压缩成**一次性的规则配置**，之后所有记忆用同一把尺子。

---

## 三、先去看论文

决定不用主观打分之后，我先去查了学界怎么做这件事。

| 论文 | 关键做法 |
|---|---|
| **REAL**（arXiv 2606.10694） | 把置信度做成一等属性 `c ∈ (0,1]`；检索只取 `c ≥ θ`；**低置信不是删除，而是「查询表达不确定时才召回」**；后续确认可升级 |
| **Agent Zero Memory**（arXiv 2608.29606） | 置信度的依据是 **provenance**（来源 + 时间戳 + 证据指针）；回答受 citation lock 约束——只能引用真正打开过的证据，不能引用就弃权 |
| **PROV-CRED** | 不同来源的 0.85 **不在同一尺度**：KGE 排序分和 LLM 自报的 0.85 不可比，不校准就没有意义 |
| **Generative Agents**（Park et al., 2023） | 检索分是**加性加权**（recency + importance + relevance，各自归一化到 [0,1]）——这印证了「不能连乘」 |

三条最有价值的结论：

1. **置信度必须由可观测的东西支撑**，否则跨来源不可比（PROV-CRED）。
2. **低置信不等于删除**，而是一种「需要更多证据才采纳」的状态（REAL）。
3. **主流排序是加性的**，不是乘性的。乘性会把小的因子放大成主导（尺度失配）。

## 四、方案：证据 → 公式

### 4.1 公式（Subjective Logic）

```
b = r / (r + s + 2)      belief（相信）
d = s / (r + s + 2)      disbelief（不信）
u = 2 / (r + s + 2)      uncertainty（不知道）
```

`r` / `s` 是支持 / 反驳证据的加权和，`+2` 是 non-informative prior。

**这个先验最关键的作用**：没有任何证据时 `b = d = 0, u = 1`（完全不确定），而不是 0/0 或 1。

系统里几千条历史记忆在引入这个模块前都没有证据记录——它们正好自动落到「未知」，**不需要给它们编一个默认分数**。这比「全给 3 分」干净得多。

### 4.2 证据从哪来：纯正则

关键的设计选择：**证据从文本里可计算地提取**，不需要改写入流程。

| 证据 | 权重 | 为什么可信 |
|---|---|---|
| payload 带 `source_path` | 0.9 | 能指回具体文件 |
| `type=git_commit` 且带提交信息 | 1.0 | 可回溯到提交 |
| 正文含 7–40 位 hex（至少含一个字母）或 `PR #N` | 1.0 | 可回溯 |
| 正文含路径 / URL | 0.8 | 可外部核验 |
| 正文含「实测 / 验证过 / 全绿」 | 0.7 | 声称有实测 |
| 正文引用另一个节点 | 0.6 | 可回溯 |
| `status=outdated`（反驳） | 1.0 | 已被明确取代 |
| 自我指涉的不确定表达（反驳） | 0.3 | 「待确认 / 待验证 / 存疑」 |

**7 位 hex 必须至少含一个字母**：git 短 hash 是 7 位，而纯 7 位数字（如日期 `2026102`）不该被当成提交号。这个细节是写测试时才发现的。

### 4.3 一个被数据推翻的直觉

我最初把「可能 / 也许 / 大概」也算作不确定信号。抽查后发现：

> 抽查 12 条含「可能」的节点，**11 条是在描述客观可能性**（「未来可能 16G」「状态可能不一致」），不是表达「这条记忆不确定」。精确率 **2/12 = 17%**。

换成只认自我指涉的表达（`待确认` / `待验证` / `存疑` / `未验证`）后，命中从 438 条降到 62 条，抽样 **8/8 全部正确**。

**这就是「语言线索」这类启发式的陷阱**：词面相似 ≠ 语义相同。

### 4.4 怎么用：只做 ε 级微调

```
final = cosine + ε_soft × (importance_norm + recency_norm)
              + ε_conf × clamp((b − 0.27) / 0.15, −1, +1)
```

用固定线性映射而不是 z-score，是为了不依赖全库统计量——检索时不必先算一遍均值 / 标准差，同一条记忆在任何库规模下得分一致。

**默认关闭**（`ε_conf = 0`），零开销。

## 五、实测（2969 条真实记忆 / 56 题）

| 方案 | Recall@5 | MRR@5 | nDCG@5 |
|---|---|---|---|
| 基线 | 0.2268 | 0.2298 | 0.2099 |
| **ε=0.05 重排** | **0.2377** (+1.09) | **0.2655** (+3.57) | **0.2482** (+3.83) |
| 硬门槛 `b ≥ 0.2` | 0.1787 (**−4.81**) | 0.2262 (−0.36) | 0.2017 (−0.81) |

bootstrap 2000 次重采样：

| 指标 | 提升 | 95% CI | 判定 |
|---|---|---|---|
| Recall@5 | +1.09pp | [−2.48, +5.56] | 不显著 |
| **MRR@5** | **+3.57pp** | **[+0.12, +7.74]** | **显著** |
| **nDCG@5** | **+3.83pp** | **[+0.76, +7.51]** | **显著** |

**置信度确实在区分好坏**：gold 节点的平均 b 是 0.404，全库平均 0.276——高 46%。

**提升全部来自语义题**（MRR 0.3796 → 0.5111，**+34.6%**）；精确标识符题完全不受影响，因为那里是字面匹配主导。

### 三条被数据否决的改动

| 改动 | 结果 |
|---|---|
| **硬门槛**（`b < 0.2` 直接过滤） | 召回 **−4.81pp**——gold 里有很多 `b=0`（没证据）的节点，过滤会误删正确答案 |
| 去掉 hedge 规则 | MRR −0.60pp |
| `tested` 权重 0.7 → 0.9 | MRR −0.90pp |
| ε ≥ 0.1 | MRR 从 0.2655 崩到 0.2149——**它只能 tie-break，不能主导排序** |

## 六、局限（写清楚比吹重要）

| 局限 | 说明 |
|---|---|
| 样本量 | 56 题、只有 7 题受影响。方向可信，具体数值别当基准 |
| 证据是粗糙代理 | 正则从正文提取，「实测」这类词约 8% 误报 |
| **未做校准** | `b = 0.8` 目前**不**意味着「80% 的情况是对的」。校准需要「置信度 vs 后来是否被推翻」的历史数据 |
| 查询侧未放行 | REAL 那篇的核心设计之一——「查询本身表达不确定时放宽门槛」——我还没实现 |

## 七、我学到的事

1. **粒度不是精度。** 5 档不比 3 档准，锚点才决定精度。
2. **判断应该被压缩，而不是被执行。** 逐条打分是执行判断；配置一次权重表是压缩判断。
3. **启发式要用数据审。** 「可能」这个词看起来像不确定，实测精确率只有 17%——不抽查就永远不知道。
4. **最难的往往不是加什么，而是拒绝加什么。** 硬门槛、更大 ε、更高权重，三个「看起来更强」的改动全部被数据否决。
