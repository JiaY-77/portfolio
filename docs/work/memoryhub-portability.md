# 记忆不该只活在一个 agent 里

> 作者：何嘉琪 ｜ 2026 年 10 月
> 对象：Palimpsest 的记忆包格式（`memoryhub` v1），示例包可直接跑
>
> **关于作者的角色**：这个格式的设计取舍是我定的（尤其是下面第四节那六条约定，每一条背后都对应一次具体的不放心）；
> 代码、敏感规则与实测由 AI 编程助手下完成。我把它写清楚，是因为「谁该为哪部分判断负责」这件事，本身就是记忆系统要回答的问题之一。

---

## 一、症状：记忆成了新的孤岛

我用自己的记忆系统已经跑了几个月。它替我记着项目决策、踩过的坑、被纠正过的错误。直到有天要做三件事：

1. 换一台机器继续工作；
2. 换一个 agent 客户端（原来那个越来越不合手）；
3. 把一段和同事共同踩过的坑，交给他看一眼。

三件事全部卡住，而且卡的方式各不相同：

- 换机器：记忆存在一个本地数据库里，带着 `.vec` / `.gidx` 一堆 sidecar 文件。拷过去能跑，但**换向量模型就得重嵌全库**——迁移一次等于重建一次。
- 换客户端：每个 agent 的记忆格式都不一样。要么写脚本硬搬字段，要么放弃，从零开始重新训练它认识我。
- 给同事看：这个最尴尬。**记忆是一条条带上下文的判断**，掰开解释就失真；不掰开又看不懂。最后我手打了三条发过去，顺序、因果关系、哪条推翻了哪条，全丢了。

问题不在于「没有导出功能」。我在的几个系统都有导出，导出成 JSON、CSV、markdown。问题在于**导出的东西不是记忆**——那是数据。

一条记忆的价值不在它的正文，在于四件事：**它是谁说的、什么时候说的、它推翻了什么、它依赖什么**。把正文抽出去，剩下的就只是一段文字。

## 二、为什么现成的方案都不合适

我先认真看了三种现成做法，每种都有明确的适用场景，也都有我不想要的东西：

| 方案 | 它好在哪 | 我不选它的原因 |
|---|---|---|
| **裸 JSON 导出**（每条记忆一个 dict） | 通用、任何语言都能读 | 丢关系、丢取代链。导入方拿到一堆平铺文本，和复制粘贴没本质区别 |
| **数据库/向量库 dump** | 完整、无损 | 绑死引擎版本。换个 embedding 维度就废，还要懂 SQLite/Rust 扩展才能读 |
| **平台私格式**（各家的 .zip / .bin） | 一键导出 | 只有那个平台能解开。等于承认「记忆只属于一个产品」 |

这三种的共同点是：**要么丢语义，要么绑实现**。而我想要的恰好是「不丢语义、也不绑实现」。

于是有了一个很朴素的要求：**一个文件，任何语言都能读，读之前不需要装任何东西，读的时候能看懂这是谁的记忆。**

## 三、一个记忆包长什么样

它是一个自包含的 JSON，三部分：manifest（元信息 + 一段给人读的故事）、nodes（节点）、edges（关系）。

```json
{
  "format": "memoryhub",
  "format_version": 1,
  "manifest": {
    "name": "示例记忆包：一个虚构的小团队 AI 助手",
    "fingerprint": "759a26d37fad6191",
    "node_total": 6,
    "edge_total": 3,
    "story": "这是一个虚构的四人小团队的 AI 助手记忆。团队只有一条硬规矩——测试要覆盖失败路径；……"
  },
  "nodes": [
    { "node_id": 101,
      "payload": { "type": "memory", "content": "用户偏好：这个项目统一用 TypeScript……",
                   "importance": 0.7, "status": "active" } }
  ],
  "edges": [
    { "source_id": 102, "target_id": 101, "label": "RELATED_TO", "weight": 1.0 }
  ]
}
```

三个字段值得单独说：

**`manifest.story`** —— 一段自然语言，说清「这个包讲的是谁、什么事」。这是我最满意的设计。因为一份记忆包**首先应该能被当故事听完**，而不是让人先读六个 JSON 对象再自己拼。技术文档里很少见这种字段，但它解决了我第一节里「给同事看」那个尴尬。

**`manifest.fingerprint`** —— 节点 + 边的稳定指纹。它不保证内容正确，只保证「这份和上次那份是不是同一份」。传文件过程中被改过、或者有人说「我用的是最新版」，用它核对一下就行。

**`node_id` 只在包内有效** —— 这是刻意设计的。包内的 id 是「在这个包里的位置」，不是「在你库里的身份」。导入方会自己分配新 id，并把原 id 记进 `origin_id`。所以**同一个包可以重复导入，不会撞 id，也不会覆盖别人的记忆**。

## 四、六条约定，每条都对应一次不放心

格式本身没什么稀奇，JSON 就是了。真正的设计在约定上——这些约束是我一条条加进去的，每一条背后都有具体的不放心：

**1. 默认零写入。**
解开一个包不需要任何权限，也不改任何东西。原因很简单：**你还不知道包里有什么，凭什么让它先写进来？** 所以 `read` 只读，`import` 不带选择参数时也只是预览。

**2. 入籍必须显式点名。**
不能「一键全收」。要写 `--select 101,102,106`，指定包内哪几条进来。这看着麻烦，但记忆是有代价的——**每收一条，我的库里就多一条要维护、要被检索、可能被误判的东西**。所以收的动作必须是有意识的。

**3. 不沿用原 id。**
新库自己分配，原 id 记进 `origin_id`，来源包记进 `origin_pack`。这样能回答「这条是从哪个包搬来的」，也不会因为 id 冲突覆盖掉本库已有的记忆。

**4. 不做冲突检测、不取代已有记忆。**
这一条最不「智能」，也最常被人问「为什么不自动合并」。因为我的系统里「取代」（`outdated`）是个**有后果的动作**：旧节点会被检索排除，但保留在版本链上供回溯。让一次文件导入顺手触发这种后果，风险太高。**导入就该是纯新增，判断留给人。**

**5. 边只保留两端都入籍的。**
上例里如果只选了 101 和 102，那么 `103 → 101` 这条边不会进来。留一条只有一端的边，图里就多一个悬空引用——检索时它会指向一个不存在的节点。**宁可少一条边，不要一条假边。**

**6. 强敏感必须显式放行。**
这条下面单独说。

## 五、敏感扫描：先读后写的另一半

「先读后写」只解决了「别乱写」。还有一半是「**别让人在不知情的情况下把凭据传出去**」。

所以解包时会扫 10 类模式，分两档：

- **强规则**（命中即拒绝，需显式 `--include-secrets` 才放行）：8 类凭据格式——OpenAI / Anthropic / Google 的 API Key、GitHub token、AWS Access Key、私钥、SSH 公钥、`Bearer` 长 token。
- **弱规则**（放行但打标记）：身份证号、手机号。

为什么分两档？因为这两类的**误判代价不一样**：

- 凭据误判为安全 = 泄露，不可逆，所以宁可错杀。
- 手机号误判为敏感 = 一条记忆进不来，代价只是重写一遍，所以不该硬拦。

弱规则命中会出现在 `secret_hint` 里供审计——记忆里出现电话号码往往是有意的（「我的紧急联系人」），系统不该替人做这个决定。

示例包里我故意留了一条写错 Key 的旧笔记，就是用来演示这个的：

```json
"issues": [ { "node_id": 105, "kind": "secret", "rules": ["openai_key"] } ]
```

它在预览里就被标出来了，不用等导入后才发现。

## 六、边界：三条我没做到的

写文档最容易犯的错，是把「没做」说成「做了」。所以这三条单独列：

**1. 不是加密。**
记忆包是明文 JSON。敏感扫描只覆盖上表那 10 类模式，**不认识的凭据格式（自研 token、内网地址、合同号、客户名单）它看不到**。发给外部之前，得自己过一遍。

**2. 不做去重。**
同一个包导入两次，会得到两份节点。要不要去重、按什么去重，是业务问题，格式不该替人决定。

**3. 不校验语义。**
它只保证结构完整、字段合法。包里写的内容对不对、有没有过期，只能靠人看 `story` 和每条 `preview` 判断。

## 七、如果重来一次，我会改什么

**会改：加一个「导出前敏感自检」。** 现在的敏感扫描发生在「读」的时候，也就是**别人的机器上**。更合理的位置是导出时——凭据本来就不该进记忆库，导出时已经晚了。这一条我打算下次改。

**不会改：六条约定里任何一条。** 尤其第 2 条（显式点名）和第 4 条（不自动取代）——它们让操作变慢，但正是这种「慢」，让记忆系统的代价变得可见。

## 八、这篇真正想说的

我做这个格式的原因，不是「我的系统比别人的好」，而是**记忆这件事迟早会遇到今天文件格式遇到过的同一个问题**：一旦你的记忆只能在一个产品里活着，它就不完全是你的。

PDF 之所以能活三十年，不是因为它设计得多好，而是因为**它的读者可以脱离作者存在**。记忆包想做的也是这件事：让一份记忆能被另一个系统读懂，哪怕那个系统还没被发明出来。

而这一步的前提，是承认记忆里有一部分东西**不可压缩**——它是谁说的、它推翻了什么、它依赖什么。把这些抽掉，导出的就只是文本，不是记忆。
