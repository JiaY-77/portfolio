# 检索融合的权重，不是调出来的

> 作者：何嘉琪 ｜ 2026 年 10 月
> 实测环境：本地 Ollama `qwen3-embedding:0.6b`（1024 维）+ SQLite FTS5（trigram），生产库 2400+ 节点
> 结论来源：生产库实测 + 融合公式推导。涉及 Palimpsest 的改动见 [PR #134](https://github.com/JiaY-77/Palimpsest/pull/134)
>
> **关于作者的角色**：我不是算法工程师，不懂 RRF 的参数推导。本文里**方向性的判断（尤其是第五节那条归一化的联想）是我的**；
> 阈值推导、代码实现、实测验证由 AI 编程助手下完成。我把这条分工写明，是因为它恰好是这篇文章真正想说的东西。

---

## 一、症状：一个查不到的 commit hash

项目的记忆检索是**双通道**的：语义向量召回 + 全文精确召回（FTS5），两路用 RRF（Reciprocal Rank Fusion）融合。

某天用一条 commit hash 去搜自己的记忆库：

```
query: d60240b PR131 squash merge commit
```

**在 FTS 通道里，目标节点排第 2 名**——精确命中，几乎完美。但在最终返回的 `top_k=60` 里，它**完全没有出现**。

第一反应是「权重调小了」：全局的 FTS 权重是 `0.1`，调大一点应该就行。我让协作的 AI 助手写了个探针去验证——**结论推翻了第一反应**。

| FTS 权重 | 目标节点总排名 | 结果 |
|---|---|---|
| `0.1`（现状） | 63 | 出局 |
| **`0.5`（"调大一点"）** | **63** | **零效果** |
| `0.94` | 约 5 | 开始有机会 |
| `1.0` | 6 | 进入前列 |

**把权重翻了 5 倍，结果一模一样。** 这说明问题不在"值不够大"。

---

## 二、病根：不是权重问题，是度量不可比

RRF 的公式极其简单：

```
score(d) = Σ_c  w_c / (k + rank_c(d))
```

- `c` 是通道（语义 / 精确）
- `rank_c(d)` 是节点在通道 c 里的名次（0-based）
- `k` 是平滑常数（业界惯例 60）

问题藏在 `rank` 这个词里。**名次是相对的，但两个通道的候选表长度差了一个数量级**：

- 语义通道：`top_k` 多少就返回多少，常是 50 条
- FTS 通道：trigram 精确命中就那么几个，常常只有 2~5 条

于是「FTS 排名第 2」和「语义排名第 2」被当成等价的名次价值来比较——可前者是「5 条里的第 2 名」，后者是「50 条里的第 2 名」，它们要去争夺同一批输出名额。

**候选表越短，每个名次的"含金量"被系统性低估。** 用权重去补这种不可比，就是在拿一个常数去修一个结构问题——所以才会有「调了没用」的怪现象。

---

## 三、把阈值算出来：中间值根本不存在

> 本节推导与实测由助手完成，我认可的是它给出的结论：**中间值没有意义，要么过阈值、要么完全无效。**

既然要判断"调多少才够"，就直接解不等式。要让一个 **FTS-only 命中**（语义通道没召回它）挤进 `top_k`，它必须打赢语义通道的第 `top_k-1` 名：

```
w_fts / (k + q)  >  w_sem / (k + top_k - 1)
```

代入 `k=60`、`q=1`（FTS 第 2 名）、`top_k=5`、`w_sem=1.0`：

```
w_fts > (60 + 1) / (60 + 4) ≈ 0.95
```

**这就是为什么 0.5 等于零**——它不满足不等式，得分 `0.5/62 ≈ 0.0081`，而语义任何一条候选都至少 `1/64 ≈ 0.0156`，差近 2 倍。响应不是连续的：`w < 0.95` 时**完全无效**，越过阈值才突然进榜。

这一点对做决策很关键：**如果先假设"响应是连续的"，就会在 0.3、0.5、0.7 之间反复试探，白花时间。** 更省的做法是先写出不等式，确认它是不是阶跃函数。

## 四、第一步决策：分档，而不是全局调参

> 分档方案是助手提出并实现的；我在这件事上的判断只有一条：**不要为了修一个窄场景去动全局参数**。

阈值算出来后，还有第二个问题：**把全局权重调成 1.0 安全吗？**

答案是不安全。FTS 的查询是 trigram 拼的（`d60 OR 024 OR 240 …`），非常宽松。权重抬到等权后，**碰巧共享几个字符**的节点也会被顶上来——自然语言查询的噪声会明显增加。

所以最终方案不是调参，而是**按查询类型分档**：

| 查询类型 | FTS 权重 | 理由 |
|---|---|---|
| 自然语言（"记忆条目的排序应该按时间"） | `0.1`（原值，不动） | 语义才是主信号，FTS 只做微调 |
| 精确标识符（`d60240b` / `PR #131` / `WEB-1234`） | `1.0` | 语义对这类 token 天然失灵，FTS 命中是最可信信号 |

判定刻意保守，三条规则：7 位以上十六进制 token（**且必须含数字**，否则 `defaced`、`decade` 这类英文词会被误判成 hash）、`#` + 数字（PR/issue 号）、大写前缀 + 数字（工单号）。判不出来就走原权重——**宁可漏判，不可误判偷改全局行为**。

修复后实测（生产库，零写入验证）：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| `d60240b PR131 squash merge commit` | top_k=60 全 MISS | 前 5 名全是 FTS 精确命中，`fts_weight=1.0` |
| 中文自然语言查询 | — | `exact_query=false`，`fts_weight=0.1`，行为完全不变 |


同时把判定结果和实际权重写进响应的 `channels` 字段——**让「走了哪条路」从响应里可见**，而不是只能翻源码。

### 系统性的验证：10 条标识符查询，修复前后对比

> 这组对照由助手设计并执行。我关心的是它能不能证明「这是整类查询失效，而不是偶发」——结论是能。

单条 query 的案例说服力有限，所以又做了一组对照：

- **评测集**：从生产库（2400+ 节点）里取 10 个真实标识符——5 个 commit hash、5 个 PR 号
- **gold 怎么定**：不做人工标注，直接枚举「FTS 索引里含该标识符的节点」作为多答案（multi-gold）——客观、可复现、换库重建也不失效
- **对照组**：同一份库副本上另起一个实例（不同端口），把精确权重用环境变量强制回 `0.1`，其余配置完全一致

| 方案 | R@5 | R@10 |
|---|---|---|
| 基线（全局权重 `0.1`） | **0 / 10** | 1 / 10 |
| 分档（标识符查询 `1.0`） | **9 / 10** | 9 / 10 |

基线那一列是 **0**——10 条精确标识符查询，一条都没能进前 5。唯一两边都失败的是 `#130`（它的 gold 在库里只有 1 个节点，且 FTS 对该 token 的命中本身不稳）。

这组数据想说明的不是「修复提升了 90%」这种漂亮数字，而是：**这不是偶发的查不到，而是整类查询在这个权重下系统性失效**——只要 query 里带精确标识符，语义通道就会把结果占满，FTS 的努力一次都不算数。

## 五、一个不懂参数的人，是怎么找到这条路的

**这一节先说清一件事**：下面的方向**不是我推导出来的**，RRF 的参数细节我看不懂，公式、验证、代码均由 AI 编程助手完成。我能贡献的是**看到实验结果时的联想**——以及判断什么该做、什么该先别做。

看到「权重调大 5 倍，结果完全一样」时，我的第一反应不是回代码里翻，而是觉得**这事我在别处见过**：

- **层归一化（LayerNorm）**：网络的每一层，激活值的分布会漂移，所以要在层内重新归一化到同一尺度
- **Adam 优化器里的 `α/√v`**：不同参数的梯度尺度差好几个数量级，一个学习率管不了所有参数，所以要用二阶矩做自适应缩放
- **注意力机制里的 `1/√d_k`**：维度变大后点积的方差跟着变大，所以要按维度缩放

这三个机制在各自领域管各自的事，但我当时的感觉是：**它们在处理同一类病——不同来源的量不能直接相加，得先归一化到同一尺度。**

于是我问了助手一句：检索融合是不是也是这个问题？语义通道一次给 50 条、精确通道只给 2 条，它们的「名次」被当成等价分量加在一起，不就是尺度不可比吗。我还顺口提了句：是不是该去找 `Attention is all you need` 这类经典论文找思路。

**助手的回答让我学到两点**：

1. 那篇论文其实不对症——`1/√d_k` 解决的是「同一张量内部维度变大导致数值爆炸」，而我们的问题是「两个异构排名表之间不可比」，属于检索融合（rank fusion）自己的问题域，有独立的文献谱系
2. 但**联想的落点是对的**：它给出的解法正是「通道内归一化」——每个通道先把自己的分数变成概率分布，再线性混合

助手推导出的形式（结论我看得懂，中间推导看不懂）：

```
p_c(d) = [1/(k+rank_c(d))] / Σ_{d'∈C_c} [1/(k+rank_c(d'))]     ← 每个通道先归一化成概率
score(d) = Σ_c  w_c · p_c(d)                                   ← 再线性混合
```

它的意义我这个层面能理解：权重终于有了物理含义——`w_sem=0.7, w_fts=0.3` 就是真·七三开，不再是「0.5 等于零效果」那种反直觉；长短候选表的偏差被归一化吸收；噪声也有天然上限（概率和为 1，一个通道塞 50 条噪声，每条只剩 1/50）。

**但我没有让它换。** 这次我学到的教训是：**读到一个漂亮的办法，和「现在就该换」是两件事。**

理由是手头的数据不够：

1. 这是检索算法的结构性改动，改错了是**全局退化**，不像调权重那样一眼能看出影响面
2. 现有的验证只有十来个实测场景，**没有评测集就证明不了「变好了」**
3. 这类项目最容易犯的错，恰恰是「读到一篇论文觉得对 → 直接换 → 没有基线 → 一年后不知道自己是变好还是变坏」

所以它被立成一个正式课题，而不是顺手改掉：

| 阶段 | 内容 | 判据 |
|---|---|---|
| ① 评测集 | 30~50 条 query × 三类（自然语言 / 精确标识符 / 混合），每条标 2~5 个可接受答案 | multi-gold：真实库里常有多个都算对的答案，单 gold 会系统性低估 |
| ② 方案对照 | 基线权重 / 分档权重 / **归一化 RRF** / 候选数补偿 | — |
| ③ 指标 | R@5、R@10、MRR、**噪声率**（top5 里不相关占比） | — |
| ④ 替换条件 | 归一化 RRF 必须在**三类 query 上都不劣于**基线 | 缺一条就不换 |

## 六、这次能复用的方法论

**属于我的（判断层）**

1. **看到反常现象，先问「这事我在别处见过吗」。** 我给的方案不是从检索领域里长出来的，是从深度学习里搬过来的——这个迁移动作恰好是产品定义者能做的、而单一领域专家容易漏掉的。
2. **分清楚「漂亮的办法」和「现在能上的办法」。** 前者让你显得有见识，后者才让系统变好。判断标准不是方法多优雅，而是**有没有基线证明它更好**；没有基线时，宁可上一个可回退的局部解并立项，也不裸换架构。

**属于执行层（助手做的，我没参与）**

3. **先算阈值，再决定要不要调参。** 很多「参数调不动」的困境，本质是没算出边界——一旦写出不等式，可能发现整个区间的努力都是无效的。
4. **先确认响应是连续还是阶跃。** 连续就细调，阶跃就直接找阈值。误判成连续，会在无效区间里反复试探。
*本文的所有数字均来自本机生产库实测；融合公式与阈值为独立推导，可复现。*
