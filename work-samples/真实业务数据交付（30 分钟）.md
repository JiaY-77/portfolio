# 真实业务数据，30 分钟内交付可验收的结论

> 一次定时实战任务：给定一个业务目标和一份**真实业务数据**，30 分钟内交出可运行的仓库与可验收的结论。
> 本文记录这次交付的**节奏、方法与我自己的判断纪律**；具体业务数据与结论已脱敏，只保留方法与可核验的做法。

---

## 一、任务形态

| 项 | 情况 |
|---|---|
| 时间 | 30 分钟（含分析 + 产出交付物 + 提交到公开仓库） |
| 数据 | 单份业务明细表（近千行、8 个字段），真实生产数据，非清洗过的教学数据 |
| 业务目标 | 一句话的业务问题，没有指定分析方法和结论 |
| 交付物 | 公开仓库：结论文档 + 可复跑脚本 + 结果表 + 图 |
| 工具约束 | 不限技术栈，允许使用 AI 工具 |

**这类任务的真实难点不是「跑不出数」，而是三件事**：数据是脏的、问题没有标准答案、时间只够做一遍。

## 二、时间表（实测）

| 阶段 | 用时 | 做的事 |
|---|---|---|
| 数据体检 | ~1 分钟 | 编码 / 分隔符 / 字段类型 / 业务角色 / 能回答什么问题 / 有哪些坑 |
| 第一轮全量分析 | ~4 分钟 | KPI、分布、分组对比、异常点 |
| 定主问题 | ~2 分钟 | 在三个候选根因里选一条主攻线（判断依据见下） |
| 定向深挖 | ~8 分钟 | 交叉验证 + 分层 + 阈值扫描 + ROI 测算 |
| 出图 | ~3 分钟 | 两张图：断层式跳变、二维交叉热力图 |
| 写结论 | ~5 分钟 | 一句话结论 + 数字速查 + 建议 + 边界 |
| 稳健性检验 | ~3 分钟 | 多变量模型、分层、时间切分、剂量反应 |
| 提交 + 提交后迭代 | ~2 分钟 | 推送仓库；随后按新发现继续补 commit |

**纪律：25 分钟必须开始提交**。宁可交付一版有边界的结论，也不要超时交一个没提交的完美分析。

## 三、数据体检：先找坑，再找数

这份数据里，三个坑如果不处理，结论会直接错：

| 坑 | 表现 | 处理 |
|---|---|---|
| 时区不一致 | 两个时间字段一个带 `+08:00`、一个是 UTC | 统一转 UTC 再相减，否则「延迟」凭空多 8 小时 |
| 空值语义 | 完成时间有 4.4% 为空，代表「未回传」而不是「失败」 | **从分母剔除**，单列说明；不假设它是成功或失败 |
| 主键重复 | 记录数比唯一 ID 多 46 条 | 按行分析（一行 = 一次决策），重复本身作为数据质量问题写进边界 |

**分母先立**：分母错一个，后面所有比率都错。我用「已回传」作分母算出 11.05%，若用全部行算是 10.56% —— 差 0.5 个百分点，但结论方向不变，所以这个选择可以解释、可以交代。

## 四、怎么选主攻线：三个候选根因，逐个检验

业务问题通常是「A 导致 B」的口语表达，但实际上 A 至少有三种不同成因，对应完全不同的动作。我把候选根因列出来，逐个做**分箱 + 目标率**，看是否单调：

| 候选根因 | 分箱后的目标率 | 判定 |
|---|---|---|
| 资源余量（账面库存） | 不单调（最充足组与 0 组几乎一样） | ❌ 不是有效信号 |
| 并发压力（排队长度） | 单调上升（0% → 26.7%） | ⚠️ 加剧因素 |
| 数据新鲜度（同步滞后） | **断层式跳变**（6.1% vs 31.5%，5.1 倍） | ✅ 主攻 |

选主攻线的标准不是「哪个 p 值小」，而是**三个条件同时满足**：

1. 与结果强相关（5.1 倍差距）
2. 可以被系统改造（不是「员工不够细心」这种无法落地的解释）
3. 有明确阈值可以变成一条规则

排队是「忙」，滞后是「看见的是旧数据」—— **「忙」只能靠加人，「看见旧数据」可以靠改同步频率**。这就是我选后者的理由。

## 五、交叉验证：证明它不是另一个变量的影子

单变量相关性最容易被质疑的一点是：「你说的滞后，会不会只是因为忙的地方都滞后？」

所以做了二维交叉：在每一档排队长度里，比较高滞后与低滞后组的缺料率。

| 排队区间 | 低滞后 | 高滞后 |
|---|---|---|
| 最低档 | 3.3% | 21.4% |
| 中档 | 5.6% | 35.3% |
| 高档 | 9.1% | 29.4% |
| 最高档 | 18.8% | 35.7% |

**每一档里高滞后都高出 2–6 倍，且在最空闲的那一档差距最大（3.3% → 21.4%）** —— 这排除了「滞后只是忙的代理变量」。

## 六、稳健性检验：主动给结论找反例

「相关 ≠ 因果」这句话写在报告里很容易，真的去验是另一回事。我做了四件事：

1. **多变量模型**：加入资源、并发、网点、品类做控制后，核心效应的比值比从 7.05 到 6.69，**几乎没动** —— 说明它不是被这些因素带出来的
2. **分层**：逐网点、逐品类看方向 —— 4/5 个网点同向、10/10 个品类同向
3. **时间切分**：用**没参与选阈值**的后两天做验证 —— 方向成立，倍数从 7.6 收窄到 3.4
4. **剂量反应**：把连续变量切成五档，看有没有台阶 —— **断崖出现在 18–30 分钟之间**（前两档 3% 左右，之后直接跳到 34%）

**两件事我刻意保留在报告里**：

- **一个反例网点**：高滞后组 5.0% 反而低于低滞后组 7.7%。样本小（缺料只 2 例），但我没删 —— 它说明机制在个别单元可能不成立
- **幅度收窄**：验证集倍数从 7.6 降到 3.4，我没有只报训练集的好数字，也正因如此，我的建议是「先试点」，不是「全面推行」

## 七、结论要能验收，不能是「建议加强管理」

最后落地的是一句话 + 一条规则 + 一笔账：

- **一句话**：根问题不是「资源不够」，而是「派工依据的数据不新鲜」
- **一条规则**：对「同步滞后超阈值」或「并发超阈值」的工单加一道风险标记；阈值不是拍的，是扫描出来的（在覆盖率和误报率之间取平衡点）
- **一笔账**：该规则覆盖约 2/3 的失败工单，用 5,000 工时换回 8,040 工时，净省约 3,040 工时/周

有阈值、有覆盖率、有净收益 —— 这样的建议可以被验收，也可以被推翻（只要有人指出口径错了）。

## 八、交付形态：结论 + 可复跑 + 迭代留痕

仓库里不只有结论：

- **结论文档**：一句话结论、数字速查表、决策路径、发现、交叉验证、稳健性检验、建议、判断的边界
- **可复跑脚本**：算数字的、画图的、出风险清单的、做稳健性检验的，分开放，都能单独跑
- **改进记录**：提交后继续迭代的每一步都留了 commit 与理由（补图 → 补风险清单 → 根因升级 → 修正一处会误导的表述 → 补稳健性检验）

**提交之后我改了一次「会误导」的表述**：原写法暗示「资源余量不重要」，实际是「这个读数被同步时间污染了」。这两句话对业务的动作完全不同，所以必须改。

## 九、这类能力的可迁移部分

1. **先体检再分析**：脏数据上的正确分析，比干净数据上的精致模型有用
2. **分母先行**：分母错了，后面全错，而且很难被发现
3. **候选根因逐个证伪**：不要一上来就验证自己想到的那个假设
4. **主动找反例**：留下不支持的证据，结论才可信
5. **结论必须可验收**：阈值 + 覆盖率 + 收益，三者缺一就是「建议关注」
6. **时间纪律**：限时任务里，先提交再优化
